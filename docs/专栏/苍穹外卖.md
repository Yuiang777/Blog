### 订单状态机建议

## 业务边界与模块设计

### 先按角色梳理用例

苍穹外卖至少包含三类参与者：

| 角色 | 核心用例 | 关键约束 |
| --- | --- | --- |
| 顾客 | 浏览菜品、购物车、下单、支付、催单、取消 | 只能操作自己的订单 |
| 商家 | 菜品管理、接单、拒单、出餐、营业设置 | 操作必须符合订单状态 |
| 配送或履约人员 | 取餐、配送、送达 | 只能处理已分配任务 |

不要直接按数据库表拆 Controller。更清晰的模块可以是：

- `catalog`：分类、菜品、套餐与售卖状态。
- `cart`：用户临时选购内容和金额试算。
- `order`：订单、明细、状态流转和超时关闭。
- `payment`：支付单、回调、退款与对账。
- `fulfillment`：接单、出餐、配送和完成。
- `account`：用户、员工、权限和门店。

模块之间通过明确的应用服务协作。订单可以保存下单时的菜品名称、单价和规格快照，避免菜单后续修改导致历史订单展示变化。

### 核心数据模型

```text
order
  id, order_no, user_id, shop_id, status
  goods_amount, delivery_fee, discount_amount, payable_amount
  address_snapshot, remark, version, created_at, paid_at

order_item
  id, order_id, dish_id, dish_name, spec_snapshot
  unit_price, quantity, subtotal

payment_order
  id, payment_no, order_id, channel, amount, status
  channel_trade_no, paid_at

order_operation_log
  id, order_id, from_status, to_status, operator_type
  operator_id, reason, created_at
```

金额使用 `DECIMAL` 或以“分”为单位的整数，不能用浮点数。订单号、支付单号和渠道流水号都应有唯一约束。

## 订单状态机

### 状态迁移表

| 当前状态 | 操作 | 下一个状态 | 操作者 | 主要副作用 |
| --- | --- | --- | --- | --- |
| 待支付 | 支付成功 | 待接单 | 支付回调 | 记录支付单、发送接单提醒 |
| 待支付 | 用户取消或超时 | 已取消 | 用户或定时任务 | 释放库存、返还优惠 |
| 待接单 | 商家接单 | 已接单 | 商家 | 记录预计出餐时间 |
| 待接单 | 商家拒单 | 已取消 | 商家 | 发起退款、恢复资源 |
| 已接单 | 出餐完成 | 待配送 | 商家 | 创建或更新配送任务 |
| 待配送 | 开始配送 | 配送中 | 配送人员 | 记录取餐时间 |
| 配送中 | 确认送达 | 已完成 | 配送人员或用户 | 记录完成时间、触发评价 |

状态迁移必须同时校验当前状态、操作者权限和业务前置条件。不要提供一个可以任意传 `status` 的通用更新接口。

```java
@Transactional
public void acceptOrder(Long orderId, Long employeeId) {
    Order order = orderRepository.findByIdForUpdate(orderId)
        .orElseThrow(() -> new NotFoundException("订单不存在"));

    if (order.getStatus() != OrderStatus.WAITING_ACCEPT) {
        throw new ConflictException("当前状态不允许接单");
    }

    order.accept(employeeId, Instant.now());
    orderRepository.save(order);
    operationLogRepository.append(orderId, "WAITING_ACCEPT", "ACCEPTED", employeeId);
}
```

高并发时可使用条件更新或乐观锁，避免两个操作同时成功：

```sql
UPDATE orders
SET status = 'ACCEPTED', version = version + 1
WHERE id = :id AND status = 'WAITING_ACCEPT' AND version = :version;
```

受影响行数为 `0` 表示状态已经改变，接口应返回冲突而不是继续执行副作用。

## 下单与支付一致性

### 下单事务边界

创建订单的一次本地事务通常包含：

1. 重新读取可售商品和价格，不能信任前端金额。
2. 校验营业状态、配送范围、库存和起送金额。
3. 计算商品金额、优惠、配送费和应付金额。
4. 创建订单及订单明细快照。
5. 扣减或预占库存。
6. 写入订单创建事件，供事务提交后异步处理。

外部支付调用不能放在数据库事务中等待。正确流程是先创建待支付订单，再创建支付单并请求支付渠道。

### 支付回调幂等

支付渠道可能重复通知、乱序通知或超时重试。处理步骤应包括：

```java
@Transactional
public void handlePaid(PaymentCallback callback) {
    signatureVerifier.verify(callback);
    PaymentOrder payment = paymentRepository.findByPaymentNoForUpdate(callback.paymentNo());

    if (payment.isPaid()) return;
    if (!payment.amountEquals(callback.amount())) {
        throw new IllegalStateException("支付金额不一致");
    }

    payment.markPaid(callback.channelTradeNo(), callback.paidAt());
    orderRepository.markPaidIfWaiting(payment.getOrderId(), callback.paidAt());
    outboxRepository.append("ORDER_PAID", payment.getOrderId().toString());
}
```

这里同时依赖支付单号唯一约束、状态判断和条件更新。回调响应应遵循支付渠道协议；业务处理成功后，即使收到重复回调也返回成功。

### 超时关闭与竞态

“定时任务关闭订单”和“支付回调”可能同时发生。可使用以下原则：

- 关闭时只更新仍为待支付的订单。
- 支付回调只将待支付订单改为待接单。
- 若订单已关闭但渠道确认支付成功，进入异常退款流程。
- 定时扫描使用分页和分片，记录每批处理数量与失败原因。

## 缓存、库存与接口设计

### 菜单缓存

分类、菜品和套餐是读多写少数据，可以按门店和分类缓存。修改菜品时先提交数据库，再删除相关缓存；读取未命中后重建并设置随机过期时间，避免大量 key 同时失效。

购物车更适合按用户隔离，缓存 key 示例：

```text
cart:{shopId}:{userId}
```

缓存只作为临时数据源。下单时仍需基于数据库中的商品状态和价格重新校验。

### 接口契约示例

```http
POST /api/orders
Idempotency-Key: 9fc0b18e-...
Content-Type: application/json

{
  "addressId": 1024,
  "items": [
    { "dishId": 31, "specId": 5, "quantity": 2 }
  ],
  "remark": "不要香菜"
}
```

成功响应包含订单号、价格明细、支付截止时间和下一步可执行动作。失败响应应区分参数错误、商品下架、库存不足、价格变化和重复请求。

## 测试、观测与复盘

### 最小测试矩阵

- 金额：正常优惠、优惠边界、配送费、价格变化。
- 状态：每个合法迁移、非法跨状态操作、重复操作。
- 支付：正常回调、重复回调、金额不符、关闭后到账。
- 权限：顾客越权访问他人订单、商家跨门店操作。
- 并发：重复提交订单、同时接单、超时关闭与支付竞态。
- 恢复：消息发送失败、退款失败、缓存不可用。

### 关键指标

| 指标 | 作用 |
| --- | --- |
| 下单成功率与 P95 延迟 | 判断核心交易链路健康度 |
| 支付回调成功率 | 发现签名、金额或渠道异常 |
| 各状态停留时长 | 找出接单、出餐和配送瓶颈 |
| 超时关闭数量 | 判断支付体验或任务调度问题 |
| 退款失败与积压 | 防止资金异常长期无人处理 |

日志至少携带 `traceId`、`orderNo`、`paymentNo` 和操作者标识，但不能记录完整手机号、地址或支付敏感信息。

## 综合示例

### 实践示例：订单状态迁移

```java
public void accept(long orderId, long merchantId) {
    Order order = repository.findForUpdate(orderId)
        .orElseThrow(OrderNotFoundException::new);
    if (!order.belongsTo(merchantId) || order.status() != PENDING_ACCEPT) {
        throw new InvalidOrderStateException();
    }
    order.accept(Instant.now());
    repository.save(order);
}
```

示例要点：

- 状态检查与修改必须位于同一事务。
- 并发场景需要悲观锁、乐观锁或条件更新。
- 状态变化应写入审计或事件记录。

## 常见误区

- 用一个布尔值表示复杂订单状态
- 接口只校验登录，不校验资源归属
- 缓存商品后忽略上下架与价格变更
- 支付回调没有签名校验和幂等处理

## 参考答案

### 1. 补充订单取消的状态迁移表。

列出允许取消的当前状态、操作者、退款需求、库存恢复、优惠回退和通知动作。

### 2. 如何保证支付回调幂等？

校验签名与金额；使用支付单号唯一约束；事务内判断当前状态；重复回调返回成功但不重复扣减或发放。

### 3. 制定项目接口文档最小字段。

方法与路径、鉴权、请求参数、响应结构、状态码、业务错误、示例、幂等与限流说明。

### 4. 如何防止两个商家操作同时把同一订单接单成功？

使用状态条件更新或乐观锁，只允许 `WAITING_ACCEPT` 状态和指定版本更新为 `ACCEPTED`；受影响行数为零时返回冲突，所有接单副作用必须在状态更新成功后执行。

### 5. 超时关闭任务和支付回调同时发生时如何处理？

两边都使用基于当前状态的原子更新。若关闭先成功而渠道确认已经收款，则进入异常退款流程；若支付先成功，关闭任务的条件更新应失败。所有分支都要记录操作日志并可补偿。
