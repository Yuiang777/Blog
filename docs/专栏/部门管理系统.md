## 需求分析与数据建模

### 明确业务规则

一个看似简单的部门 CRUD，也应先写清规则：

- 部门名称在同一组织内不能重复。
- 部门可以有上级，但不能把自己或自己的子部门设为上级。
- 负责人必须是当前组织中有效的员工。
- 存在子部门或在职员工时，不允许直接删除。
- 停用部门后不能再分配新员工，但历史数据仍可查询。
- 所有写操作保留创建人、修改人和时间。

这些规则决定唯一索引、外键、校验顺序和接口错误码。不要等到 Controller 写完才补业务约束。

### 表结构示例

```sql
CREATE TABLE department (
    id          BIGINT PRIMARY KEY,
    org_id      BIGINT       NOT NULL,
    parent_id   BIGINT       NULL,
    name        VARCHAR(64)  NOT NULL,
    leader_id   BIGINT       NULL,
    status      VARCHAR(16)  NOT NULL DEFAULT 'ENABLED',
    sort_order  INT          NOT NULL DEFAULT 0,
    version     INT          NOT NULL DEFAULT 0,
    created_by  BIGINT       NOT NULL,
    created_at  TIMESTAMP    NOT NULL,
    updated_by  BIGINT       NOT NULL,
    updated_at  TIMESTAMP    NOT NULL,
    CONSTRAINT uk_department_org_name UNIQUE (org_id, name),
    CONSTRAINT ck_department_status CHECK (status IN ('ENABLED', 'DISABLED'))
);

CREATE INDEX idx_department_parent ON department(org_id, parent_id, sort_order);
```

如果数据库或团队约定不使用物理外键，应用层仍需实现同等的引用完整性检查，并通过测试覆盖。

## 接口与对象边界

### 不要直接暴露数据库实体

建议区分四类对象：

| 对象 | 作用 | 示例 |
| --- | --- | --- |
| Command / Request DTO | 接收并校验写请求 | `CreateDepartmentRequest` |
| Query | 描述查询条件 | `DepartmentPageQuery` |
| Domain / Entity | 承载状态和业务行为 | `Department` |
| Response / View | 稳定返回结构 | `DepartmentDetailResponse` |

```java
public record CreateDepartmentRequest(
    @NotNull Long orgId,
    Long parentId,
    @NotBlank @Size(max = 64) String name,
    Long leaderId,
    @Min(0) Integer sortOrder
) {}
```

实体字段变化不应意外改变 API；请求对象也不能让客户端修改 `createdBy`、`version` 等服务端字段。

### RESTful 接口

```text
POST   /api/departments              创建部门
GET    /api/departments/{id}         查询详情
GET    /api/departments              分页或条件查询
PATCH  /api/departments/{id}         修改名称、负责人等
POST   /api/departments/{id}/disable 停用部门
DELETE /api/departments/{id}         删除空部门
```

状态操作具有业务语义时，使用明确动作接口比让客户端随意 PATCH `status` 更安全。

响应状态建议：创建成功 `201`，查询成功 `200`，删除成功 `204`，参数错误 `400`，未认证 `401`，无权限 `403`，不存在 `404`，版本或状态冲突 `409`。

### 统一错误结构

```json
{
  "code": "DEPARTMENT_NAME_DUPLICATED",
  "message": "同一组织内部门名称不能重复",
  "traceId": "9d64a7...",
  "fieldErrors": [
    { "field": "name", "message": "该名称已存在" }
  ]
}
```

业务错误码要稳定，前端不应通过匹配中文 message 判断逻辑。

## Service 业务实现

### 创建部门

```java
@Transactional
public Long create(CreateDepartmentRequest request, Operator operator) {
    organizationPolicy.checkWritable(request.orgId(), operator);

    if (request.parentId() != null) {
        Department parent = departmentRepository.require(request.parentId());
        parent.ensureBelongsTo(request.orgId());
        parent.ensureEnabled();
    }

    employeePolicy.checkLeader(request.orgId(), request.leaderId());
    departmentRepository.ensureNameAvailable(request.orgId(), request.name(), null);

    Department department = Department.create(request, operator.userId(), clock.instant());
    departmentRepository.insert(department);
    auditLog.append("DEPARTMENT_CREATED", department.getId(), operator.userId());
    return department.getId();
}
```

应用层先给出友好校验，但数据库唯一约束仍是并发下最终防线。捕获唯一约束异常时，将其转换为稳定的 `409` 业务错误。

### 修改与乐观锁

```sql
UPDATE department
SET name = #{name},
    leader_id = #{leaderId},
    version = version + 1,
    updated_by = #{operatorId},
    updated_at = #{updatedAt}
WHERE id = #{id} AND version = #{version};
```

受影响行数为 `0` 时重新查询：不存在返回 `404`，版本不同返回 `409`。不能把并发覆盖悄悄当作修改成功。

### 安全删除

删除前依次检查子部门、员工和其他业务引用。若审计要求较高，可以使用逻辑删除或“停用”代替物理删除。

```java
@Transactional
public void delete(Long id, Operator operator) {
    Department department = departmentRepository.requireForUpdate(id);
    permission.checkManage(department.getOrgId(), operator);
    if (departmentRepository.existsChild(id)) throw new ConflictException("请先处理子部门");
    if (employeeRepository.existsActiveByDepartment(id)) throw new ConflictException("请先转移在职员工");
    departmentRepository.delete(id);
}
```

## MyBatis 查询实践

### 动态条件查询

```xml
<select id="findPage" resultMap="DepartmentResultMap">
  SELECT id, org_id, parent_id, name, leader_id, status,
         sort_order, version, created_at, updated_at
  FROM department
  <where>
    org_id = #{query.orgId}
    <if test="query.parentId != null">
      AND parent_id = #{query.parentId}
    </if>
    <if test="query.keyword != null and query.keyword != ''">
      AND name LIKE CONCAT('%', #{query.keyword}, '%')
    </if>
    <if test="query.status != null">
      AND status = #{query.status}
    </if>
  </where>
  ORDER BY sort_order ASC, id ASC
</select>
```

排序字段不能直接接受客户端字符串拼接。需要动态排序时，使用白名单映射。关键词模糊查询数据量大时应评估索引和搜索方案。

### 避免 N+1 查询

列表需要负责人姓名时，不要循环查询员工。可以一次 join，或先收集 `leaderId` 批量查询后在内存组装。是否 join 取决于模块边界、数据量和一致性要求。

树形部门可以一次查询组织下的全部节点，再按 `parentId` 构建：

```java
Map<Long, List<DepartmentNode>> children = nodes.stream()
    .collect(Collectors.groupingBy(node -> Objects.requireNonNullElse(node.parentId(), 0L)));
```

构建前应检测孤儿节点和环，避免脏数据导致无限递归。

## 权限、审计与测试

### 权限边界

- Controller 只确认当前身份，不直接信任请求中的 `orgId`。
- Service 根据资源所属组织再次校验操作权限。
- 普通用户可以读取组织树，但只有管理员或授权负责人能写。
- 批量导出和敏感人员信息使用更细粒度权限。

### 审计日志

记录谁在什么时间对哪个部门执行了什么操作，并保存必要的变更前后摘要。日志不能由客户端提供，且不应与普通应用日志混为一谈。

### 测试分层

```text
单元测试：名称规范化、状态规则、父子关系和权限策略
Mapper 测试：resultMap、动态 SQL、唯一约束和乐观锁
Service 集成测试：事务回滚、并发修改、安全删除
API 测试：参数校验、状态码、错误结构和越权访问
```

至少覆盖：重名创建、上级不存在、负责人无效、形成环、并发修改、存在员工时删除、跨组织访问和空查询结果。

## 综合示例

### 实践示例：创建部门接口

```java
@PostMapping("/departments")
ResponseEntity<DepartmentView> create(@Valid @RequestBody CreateDepartmentRequest request) {
    DepartmentView created = departmentService.create(request);
    URI location = URI.create("/departments/" + created.id());
    return ResponseEntity.created(location).body(created);
}
```

示例要点：

- 成功创建资源返回 201，并通过 Location 指向新资源。
- 请求 DTO 与持久化实体分离。
- 部门名称唯一性应由数据库唯一约束兜底。

## 常见误区

- 所有接口都使用 POST
- 直接把数据库实体作为外部请求和响应
- 只在代码中检查唯一性，没有数据库约束
- 删除部门时不检查关联员工或业务规则

## 参考答案

### 1. 设计部门资源的五个基础接口。

POST /departments；GET /departments；GET /departments/{id}；PUT 或 PATCH /departments/{id}；DELETE /departments/{id}。

### 2. 三种 MyBatis 映射方式如何选择？

字段一致时开启驼峰映射；少量特殊字段可用别名；复杂或复用映射使用 resultMap。

### 3. 为项目设计最小测试集。

创建成功与重名；查询存在与不存在；修改校验；有关联数据时删除失败；Mapper 映射正确。

### 4. 修改上级部门时如何避免形成循环关系？

禁止选择自己作为上级，并从候选上级沿 `parentId` 向根节点遍历；途中遇到当前部门即拒绝。还应设置最大深度并检测脏数据中的既有环。

### 5. 乐观锁更新返回零行时，接口应该如何响应？

重新查询资源：不存在返回 `404`，资源存在但版本不同返回 `409 Conflict`，同时提示客户端刷新后重新提交，不能静默覆盖新版本数据。
