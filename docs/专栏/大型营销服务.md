### 项目概览

#### 大型营销服务（专栏）

#### 项目定位

- 目标：用 DDD（领域驱动设计）落地营销活动/抽奖等业务
- 特点：规则复杂、策略多、并发高、数据一致性要求强

#### 领域视角（建议拆分）

- 活动域：活动创建、审核、发布、生命周期
- 策略域：抽奖策略装配、权重与概率分发
- 规则域：前置/中置/后置规则过滤与组合
- 库存域：不超卖、可回收、可观测

#### 关键实现记录（摘录）

##### 策略概率装配

思路：

- 将奖品概率离散为“位置数组/列表”
- 通过乱序分布来实现 O(1) 抽取
- 结果与权重策略写入 Redis，运行期快速读取

##### 规则过滤：责任链

适用场景：规则可插拔、顺序可编排、链式短路。

##### 规则模型：决策树

适用场景：规则需要按节点条件分支，最终导向某个结果（奖品/兜底）。

##### 库存不超卖（Redis）

建议：

- 先装配库存到缓存
- 扣减采用原子操作 + 凭证/过期自愈
- 异步落库与对账兜底

## 营销系统领域设计补充

### 核心领域对象

```text
Campaign        活动：时间、状态、预算和适用渠道
Strategy        策略：抽奖方式、权重和规则入口
Rule            规则：准入、次数、黑名单、库存等判断
Prize           奖品：类型、发放方式和展示信息
PrizeStock      库存：可用量、锁定量和已发放量
Participation   参与记录：用户、活动、请求号和结果
AwardOrder      发奖单：奖品、收件目标、状态和重试信息
```

活动配置、抽奖决策和奖品发放属于不同生命周期。抽奖成功不代表发奖已经成功，应通过发奖单持续追踪。

### 活动状态机

```text
DRAFT -> READY -> RUNNING -> PAUSED -> FINISHED
                  |             |
                  +-----------> CLOSED
```

- 草稿允许编辑全部配置。
- 就绪状态完成规则、奖品、库存和时间校验。
- 运行中只允许少量安全变更，并保留版本。
- 暂停拒绝新参与，但不影响已创建发奖单处理。
- 结束或关闭后配置不可随意恢复。

状态迁移记录操作者、原因、前后版本和时间，便于审计。

## 一次抽奖的完整流程

1. 校验活动状态、渠道、时间和用户身份。
2. 使用请求号完成入口幂等检查。
3. 判断用户资格、黑名单、参与次数和频率。
4. 加载已发布策略版本，执行规则树。
5. 根据权重或保底规则得到候选奖品。
6. 原子扣减对应库存；失败时执行降级奖品或未中奖。
7. 保存参与记录、抽奖结果和 Outbox 事件。
8. 异步创建发奖单并调用具体奖品渠道。
9. 更新发奖状态，失败按规则重试或人工处理。

主链路只做决定结果必须完成的步骤。短信、统计、排行榜等放到事件下游，避免拖慢抽奖响应。

## 幂等与参与次数

### 请求幂等

客户端为一次用户动作生成唯一请求号：

```sql
CREATE UNIQUE INDEX uk_participation_request
ON participation(activity_id, user_id, request_id);
```

重复请求返回首次抽奖结果，不能再次扣次数和库存。幂等记录、次数扣减、结果保存处于同一本地事务。

### 次数账户

次数可能来自每日赠送、任务奖励和补偿。相比只保存一个剩余数字，流水模型更容易审计：

```text
participation_quota
  activity_id, user_id, available_count, version

quota_ledger
  ledger_no, activity_id, user_id, change_count
  reason, source_id, balance_after, created_at
```

条件更新避免超扣：

```sql
UPDATE participation_quota
SET available_count = available_count - 1,
    version = version + 1
WHERE activity_id = ?
  AND user_id = ?
  AND available_count > 0
  AND version = ?;
```

## 规则引擎与策略版本

### 规则树

规则节点输入稳定上下文，输出通过、拒绝或下一节点：

```java
public sealed interface RuleResult permits Passed, Rejected, Routed {}

public interface RuleNode {
    RuleResult evaluate(DrawContext context);
}
```

规则示例：活动准入、用户等级、地域、黑名单、参与次数、库存、保底和风控分。每个节点记录规则 ID、版本、耗时和结果，但不能在日志中泄露完整用户画像。

### 配置发布

运行中请求绑定一个不可变策略版本：

```text
strategy_version
  strategy_id
  version
  config_snapshot
  status       # DRAFT / PUBLISHED / RETIRED
  checksum
  published_at
```

编辑产生新草稿，校验通过后原子发布。已经开始的请求继续使用原版本，避免一次抽奖过程中规则变化。

### 权重算法

整数权重可以使用累计区间：

```java
int cursor = random.nextInt(totalWeight);
int cumulative = 0;
for (PrizeWeight item : candidates) {
    cumulative += item.weight();
    if (cursor < cumulative) return item.prizeId();
}
throw new IllegalStateException("权重配置不完整");
```

上线前验证权重非负、总和大于零、奖品有效。使用固定随机种子进行单元测试，并用大量模拟检查分布是否接近期望，但模拟不能代替库存约束。

## 库存一致性

### Redis 预扣

Lua 将检查与扣减合并：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock <= 0 then
  return 0
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

`KEYS[2]` 保存已处理请求，防止重复预扣。脚本短小并设置业务 key 过期和容量治理。

### 数据库最终账本

Redis 提供高并发入口，但数据库保存最终库存与发放流水：

```sql
UPDATE prize_stock
SET issued_count = issued_count + 1,
    available_count = available_count - 1,
    version = version + 1
WHERE prize_id = ?
  AND available_count > 0;
```

通过唯一发奖单号和条件更新保证最终不超发。Redis 成功而数据库失败时，进入补偿队列；补偿本身也必须幂等。

### 库存分片

极端热点奖品可以分成多个库存桶降低单 key 压力。请求按稳定算法选择桶，桶空时尝试有限次其他桶。系统还需汇总剩余库存，并防止某些桶长期闲置。

## 发奖系统

### 发奖单状态

```text
CREATED -> PROCESSING -> SUCCEEDED
             |
             +-> RETRYING -> FAILED -> MANUAL
```

不同奖品渠道通过统一接口适配：

```java
public interface AwardHandler {
    AwardType supports();
    AwardResult issue(AwardCommand command);
}
```

优惠券、积分、实物和第三方卡密的失败语义不同。发奖结果必须区分明确失败、处理中和未知，未知结果先查询渠道状态，不能盲目重复发放。

### 重试策略

- 网络超时、限流等瞬时错误指数退避重试。
- 参数错误、账号不存在等不可恢复错误直接失败。
- 每次调用携带稳定业务单号，依赖渠道幂等。
- 达到上限进入人工处理并告警。
- 补发、取消和人工修改记录完整审计。

## 事务与事件

### Outbox

参与结果与待发布事件写在同一事务：

```sql
BEGIN;

INSERT INTO participation(...);
INSERT INTO draw_result(...);
INSERT INTO event_outbox(event_id, event_type, aggregate_id, payload, status)
VALUES (?, 'PrizeWon', ?, ?, 'NEW');

COMMIT;
```

发布器异步发送，消费者通过事件 ID 幂等。监控最老未发布事件年龄，避免数据库成功但发奖链路长期停滞。

### 对账与补偿

定时对账比较：参与中奖记录、库存流水、发奖单和渠道结果。差异进入补偿工单，不直接用脚本无审计地修改生产数据。

## 风控与防刷

### 多层防护

- 网关：IP、设备和账号速率限制。
- 业务：参与资格、每日次数、活动总预算。
- 风控：设备指纹、异常账号关系、行为频率和风险分。
- 发奖：高价值奖品二次校验、延迟发放或人工审核。

不能只按 IP 限流，共享网络会误伤；也不能只靠前端按钮禁用，所有限制必须服务端执行。

### 隐私与审计

只收集完成风控所需数据，设置保留期限和访问权限。日志中对手机号、地址、身份证和设备标识脱敏。规则命中原因对内部可审计，对外响应避免泄露可被绕过的细节。

## 测试与容量验证

### 测试矩阵

- 权重：边界、零权重、总权重错误和分布模拟。
- 次数：重复请求、并发扣减、跨天重置和补偿。
- 库存：最后一个库存、Redis 故障、数据库失败和重放。
- 发奖：成功、超时、明确失败、未知结果和人工补发。
- 状态：活动暂停、结束、版本切换和时区边界。
- 风控：正常用户、突发请求、共享 IP 和高风险奖品。

### 压测指标

不仅看 QPS，还要观察：抽奖 P95/P99、规则节点耗时、库存失败率、数据库连接、Redis 热 key、消息积压、发奖成功率和补偿量。

压测数据和渠道必须隔离生产真实奖品，避免测试触发真实发放。

## 运行监控

| 指标 | 目的 |
| --- | --- |
| 活动参与量、成功率 | 判断入口与业务健康度 |
| 各规则拒绝比例 | 发现配置或风控异常 |
| 奖品命中与库存余额 | 防止分布漂移和超发 |
| 发奖成功率、最老待发奖年龄 | 发现渠道和积压问题 |
| Outbox、重试、补偿数量 | 发现最终一致性链路异常 |
| 单用户/IP/设备异常频率 | 识别攻击与误伤 |

任何配置发布都记录版本并与指标时间线关联，出现异常可以快速回退到上一策略版本。

## 常见误区

- 领域对象按数据库表一一映射，缺少业务行为
- 只描述成功路径，不记录失败、重试和补偿
- 开发日志没有指标、证据或决策背景
- 抽奖概率、规则与库存代码耦合在一个流程中

## 参考答案

### 1. 画出一次抽奖的时序图。

至少包含资格校验、策略装配、随机抽取、库存扣减、结果落库、发奖和失败补偿。

### 2. 如何验证不超卖？

使用大于库存量的并发请求；验证成功数不超过库存、重复请求幂等、Redis 与数据库最终一致，并注入超时和重启故障。

### 3. 从日志中选一次迭代写 ADR。

补齐背景、候选方案、选择理由、代价、验证结果和后续观察指标。

### 4. 为什么运行中的抽奖请求要绑定不可变策略版本？

一次抽奖会跨越多个规则节点和库存步骤，如果中途读取到新配置，结果将不可复现且可能违反权重或资格约束。绑定版本可保证整次决策一致、可审计和可回放。

### 5. 营销系统对账需要比较哪些关键记录？

比较参与记录、抽奖结果、库存流水、发奖单、渠道最终状态和 Outbox 发布状态；按业务单号识别缺失、重复和状态不一致，再通过幂等补偿或人工工单处理。
