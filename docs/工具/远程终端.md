## 核心内容

### SSH 安全基线

1. 优先使用密钥认证，并为私钥设置口令。
2. 首次连接核对主机指纹，不盲目接受变化的指纹。
3. 禁止使用 root 进行日常操作；通过 sudo 获取临时权限。
4. 不在会话记录、脚本或仓库中保存明文密码。

## SSH 连接原理与配置

### 一次连接经历了什么

SSH 连接不是“输入密码后直接进入服务器”，而是依次完成以下阶段：

1. **名称解析**：将域名解析为 IP。
2. **TCP 建连**：客户端连接服务器的 SSH 端口，默认是 `22`。
3. **算法协商**：双方选择密钥交换、主机密钥、加密和完整性算法。
4. **主机校验**：客户端检查服务器指纹，防止连接到伪造主机。
5. **用户认证**：使用密钥、密码或其他认证方式确认用户身份。
6. **会话建立**：创建交互式 Shell、执行单条命令或建立隧道。

因此排错也应按这个顺序进行。连端口都不通时，不应该反复修改私钥；出现 `Permission denied` 时，说明 TCP 和 SSH 握手通常已经成功，应检查用户名、密钥和服务端授权。

### 推荐的客户端配置

将常用连接写入 `~/.ssh/config`，可以减少手工输入并避免连接错环境：

```sshconfig
Host blog-prod
    HostName 203.0.113.10
    User deploy
    Port 22
    IdentityFile ~/.ssh/blog_prod_ed25519
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3

Host blog-test
    HostName 10.10.2.15
    User deploy
    IdentityFile ~/.ssh/blog_test_ed25519
    ProxyJump bastion

Host bastion
    HostName bastion.example.com
    User ops
    IdentityFile ~/.ssh/bastion_ed25519
```

之后可直接执行 `ssh blog-prod`。`IdentitiesOnly yes` 可以避免客户端尝试过多密钥而被服务器提前拒绝；保活参数用于及时发现已经失效的连接，但不能替代应用层健康检查。

### 主机指纹如何管理

首次连接显示的指纹必须通过可信渠道核对，例如云控制台、管理员提供的资产清单或服务器本机输出：

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

服务器重装后指纹会变化。不要直接使用 `ssh-keygen -R` 后无条件接受新指纹，应先确认变更记录，再清理旧条目：

```bash
ssh-keygen -R 203.0.113.10
ssh-keyscan -H 203.0.113.10 >> ~/.ssh/known_hosts
```

`ssh-keyscan` 只负责获取公钥，本身不能证明公钥可信，仍需比对指纹。

## 密钥、权限与最小授权

### 生成独立密钥

```bash
ssh-keygen -t ed25519 -a 64 -f ~/.ssh/blog_prod_ed25519 -C "blog-prod-deploy"
```

- 私钥只保存在可信客户端，并设置口令。
- 公钥写入服务器用户的 `~/.ssh/authorized_keys`。
- 测试、生产、个人和自动化任务使用不同密钥，便于独立吊销。
- 自动化密钥只授予完成任务所需的命令和目录权限。

Linux 服务端常见权限要求：

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chown -R deploy:deploy ~/.ssh
```

权限过宽时，OpenSSH 可能拒绝读取授权文件。还要检查父目录所有者、SELinux 上下文以及 `sshd_config` 中的 `AuthorizedKeysFile`。

### 限制自动化密钥

可以在 `authorized_keys` 的公钥前增加限制：

```text
from="198.51.100.20",no-agent-forwarding,no-port-forwarding,no-pty ssh-ed25519 AAAA... ci-deploy
```

这能限制来源地址和可用能力。若密钥仅用于备份，还可通过 `command="/usr/local/bin/run-backup"` 固定允许执行的命令。

## 跳板机与端口转发

### 使用跳板机访问内网

生产数据库和应用节点通常不直接暴露公网。推荐使用 `ProxyJump`：

```bash
ssh -J ops@bastion.example.com deploy@10.10.2.15
```

相比先登录跳板机再手工执行第二次 SSH，`ProxyJump` 不需要把目标服务器私钥复制到跳板机，密钥仍保留在本机。

### 本地端口转发

将远端只能在内网访问的 MySQL 映射到本机：

```bash
ssh -N -L 13306:10.10.3.20:3306 blog-prod
```

本机应用连接 `127.0.0.1:13306`，流量会通过 SSH 到达内网 MySQL。`-N` 表示不启动远程 Shell。转发只应监听本地回环地址，不要随意加 `-g` 暴露给局域网。

### 远程端口转发

让远端临时访问本机服务：

```bash
ssh -N -R 18080:127.0.0.1:8080 blog-test
```

远程转发常用于临时联调，不适合作为长期生产入口。结束后立即关闭，并确认服务端 `GatewayPorts` 没有扩大监听范围。

## 文件传输与安全发布

### SCP、SFTP 与 rsync 如何选择

| 工具 | 适用场景 | 特点 |
| --- | --- | --- |
| `scp` | 少量文件的一次性复制 | 简单，但增量和恢复能力弱 |
| `sftp` | 交互式浏览与上传下载 | 权限清晰，适合人工操作 |
| `rsync` | 目录同步、增量发布 | 支持校验、排除规则和断点续传 |

使用 rsync 发布静态文件：

```bash
rsync -avz --delete-delay \
  --exclude='.env' \
  --exclude='logs/' \
  ./dist/ blog-prod:/srv/blog/releases/20260819/
```

`--delete-delay` 会删除目标端多余文件，使用前必须先加 `--dry-run` 检查范围。配置、密钥、日志和用户上传目录不应混入构建产物同步。

### 原子替换与回滚

推荐以版本目录保存发布产物，再切换软链接：

```bash
ln -sfn /srv/blog/releases/20260819 /srv/blog/current.new
mv -Tf /srv/blog/current.new /srv/blog/current
nginx -t && systemctl reload nginx
```

出现异常时，把 `current` 切回上一版本并重新加载服务。数据库变更必须另外设计向前兼容与回滚策略，不能只回滚代码目录。

## 分层排错手册

### 网络与端口

```bash
Resolve-DnsName example.com          # Windows DNS
Test-NetConnection example.com -Port 22
nc -vz example.com 22                # Linux / macOS
```

超时通常是路由、防火墙、安全组或端口错误；立即拒绝通常表示目标可达，但端口没有监听或被主动拒绝。

### SSH 握手与认证

```bash
ssh -vvv blog-prod
```

重点观察：

- `Connecting to`：最终连接的 IP 和端口是否正确。
- `Server host key`：主机密钥类型和指纹。
- `Offering public key`：客户端实际尝试了哪把密钥。
- `Authentications that can continue`：服务端允许哪些认证方式。
- `Permission denied`：用户名、密钥、公钥部署或权限存在问题。

### 服务端检查

```bash
sudo ss -lntp | grep ':22'
sudo sshd -t
sudo journalctl -u ssh -n 100 --no-pager
sudo tail -n 100 /var/log/auth.log
```

先用 `sshd -t` 校验配置，再重载服务。修改 SSH 端口或认证方式时保留当前会话，另开终端验证新连接成功后再退出，避免把自己锁在服务器外。

## 综合示例

### 综合示例：本地 SSH 配置

```bash
Host blog-server
  HostName 203.0.113.10
  User deploy
  Port 22
  IdentityFile ~/.ssh/blog_ed25519
  ServerAliveInterval 60
```

示例要点：

- 示例 IP 属于文档保留地址，需要替换为真实服务器。
- 为不同环境使用不同 Host 别名和密钥。
- 密钥文件权限应限制为当前用户读取。

## 常见误区

- 使用 root 和弱密码直接暴露公网 SSH
- 忽略主机指纹突然变化
- 上传配置文件时覆盖生产环境密钥
- 遇到连接失败只重启服务，不检查网络、端口和日志

## 参考答案

### 1. 如何判断是网络不通还是 SSH 认证失败？

先检查 DNS、路由和端口连通性，再使用 `ssh -v` 查看握手与认证阶段；认证失败说明网络连接通常已建立。

### 2. 为什么要使用不同环境的独立密钥？

降低单个密钥泄露的影响范围，便于单独吊销和审计。

### 3. 上传新配置的安全步骤是什么？

先上传到临时路径，校验内容和权限，备份旧配置，原子替换，验证服务后保留回滚入口。

### 4. 为什么通过 `ProxyJump` 访问内网比把私钥复制到跳板机更安全？

`ProxyJump` 只让跳板机转发连接，目标服务器私钥仍留在本机。即使跳板机被入侵，攻击者也更难直接取得可长期复用的目标主机凭证。

### 5. 收到 `Permission denied (publickey)` 时应该按什么顺序排查？

先用 `ssh -vvv` 确认实际用户名、目标地址和客户端提供的密钥，再检查服务端 `authorized_keys` 内容、目录权限与所有者，最后检查 `sshd_config`、认证日志和安全策略。
