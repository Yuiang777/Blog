### 分布式基础、Dubbo 与 ZooKeeper

#### 微服务组件笔记

#### 分布式与微服务基础

##### 常见性能指标

- 响应时间：一次请求从发起到响应的总耗时
- 并发：同一时间系统处理请求的能力
- 吞吐量：单位时间内系统能处理的请求数量（QPS/TPS）

##### 集群 vs 分布式

- 集群：多台机器干同一件事（同一个模块多实例部署）
- 分布式：多台机器干不同的事（拆分模块后协作完成一个系统）

演进路径（常见说法）：

单体 -> 垂直化 -> 分布式（RPC）-> SOA -> 微服务

## 服务拆分与边界

### 什么时候不该拆

微服务不是项目规模变大后的默认答案。以下情况更适合先保持模块化单体：

- 团队很小，业务边界仍频繁变化。
- 没有自动化测试、持续交付和监控基础。
- 数据强耦合，大量功能依赖跨模块事务。
- 当前瓶颈来自慢 SQL 或错误设计，而不是部署边界。
- 拆分后并不能获得独立扩容、发布或团队自治价值。

模块化单体同样可以按领域分包、限制依赖和明确接口。当模块边界经过业务验证，再提取为独立服务，成本更可控。

### 拆分依据

优先围绕业务能力和数据所有权拆分，而不是按 Controller、Service、DAO 技术层拆分。可使用以下问题检查：

1. 这个能力是否有独立术语、规则和生命周期？
2. 是否由一个团队负责并能独立发布？
3. 是否有不同的吞吐、可用性或合规要求？
4. 数据能否由该服务独占写入？
5. 拆分后跨服务调用是否比原模块调用更少、更稳定？

订单服务可以拥有订单数据，库存服务拥有库存数据。其他服务通过 API 或事件获取所需信息，不能绕过服务直接写对方数据库。

## 服务契约设计

### HTTP 与 RPC 的边界

- 面向浏览器、开放平台或多语言生态时，HTTP/JSON 通常更通用。
- 内部高性能调用可使用 Dubbo 或 gRPC，但仍需版本、超时、鉴权和可观测性。
- 同一次用户请求中需要立即结果的操作用同步调用。
- 可以延迟处理、允许最终一致的业务事实用事件传递。

契约必须明确：输入输出、错误码、幂等要求、超时上限、分页、版本兼容和降级行为。

### 向后兼容

安全的演进通常是先新增可选字段，等待消费者升级，再停用旧字段。直接改名、改变类型或改变字段语义会破坏旧客户端。

```json
{
  "orderId": "ORDER-001",
  "status": "PAID",
  "paidAt": "2026-08-19T08:30:00Z",
  "extensions": {}
}
```

消费者应忽略未知字段；生产者不能依赖消费者立刻理解新字段。关键契约应在 CI 中执行消费者契约测试。

## 服务发现、配置与网关

### 服务发现

注册中心维护服务实例和健康状态，调用方通过服务名发现可用实例。需要区分：

- 注册成功不等于业务健康。
- 心跳正常不等于依赖数据库可用。
- 客户端缓存实例列表时要处理注册中心短暂不可用。
- 下线前先从流量入口摘除，再等待在途请求结束。

### 配置管理

配置分为普通配置和秘密：

- 普通配置可以进入配置中心并保留版本、审计和回滚。
- 密码、令牌和私钥进入专门的 Secret 管理系统，日志中必须脱敏。
- 动态配置要说明生效范围、默认值和回滚行为。
- 影响线程池、超时和限流的配置变更必须灰度验证。

### API 网关

网关适合统一处理路由、认证、限流、跨域、访问日志和协议适配，但不能堆积核心业务逻辑。网关自身必须多实例部署，并设置请求体、连接数、超时和上传大小限制。

## 容错设计

### 超时预算

没有超时的远程调用可能无限占用线程和连接。上游总超时必须大于下游超时与本地处理时间之和，并预留网络抖动：

```text
用户请求预算 1500ms
  订单服务本地处理 150ms
  库存调用预算 350ms
  优惠调用预算 300ms
  支付预下单预算 450ms
  序列化、网络和余量 250ms
```

如果每一层都设置 2 秒超时，五层调用可能让用户等待远超预期。应从入口 SLA 反向分配预算。

### 重试

只对瞬时错误和幂等操作重试。建议使用指数退避、随机抖动、次数上限和总时间预算：

```java
RetryPolicy policy = RetryPolicy.builder()
    .maxAttempts(3)
    .initialDelay(Duration.ofMillis(80))
    .maxDelay(Duration.ofMillis(400))
    .retryOn(Set.of(TIMEOUT, CONNECTION_RESET))
    .build();
```

不要对参数错误、权限错误和明确的业务拒绝重试。多层同时重试会形成放大，应明确只由哪一层负责。

### 熔断、隔离与限流

- **熔断**：错误率或慢调用超过阈值时短暂拒绝请求，让下游恢复。
- **隔离**：不同依赖使用独立线程池、连接池或信号量，避免一个依赖拖垮全部请求。
- **限流**：控制入口或关键资源的请求速率，保护系统容量。
- **降级**：返回缓存、默认值或关闭非核心能力，但不能伪造交易成功。

熔断器应有关闭、打开、半开状态，并监控触发原因、持续时间和恢复结果。

## 分布式数据一致性

### 避免跨库强事务

微服务通常通过本地事务加事件实现最终一致。以下单为例：

1. 订单服务创建待确认订单并写入 Outbox。
2. 库存服务收到事件后预占库存。
3. 优惠服务冻结优惠资格。
4. 全部成功后订单进入待支付；失败则执行补偿。

每个步骤必须幂等，并保存当前流程状态。补偿不是数据库回滚，而是一个新的业务动作，例如释放库存或返还优惠券。

### Saga 状态表示例

```text
order_saga
  saga_id
  order_id
  current_step
  status          # RUNNING / SUCCEEDED / COMPENSATING / FAILED
  retry_count
  next_retry_at
  last_error
  version
```

编排式 Saga 由协调者决定下一步，流程直观但协调者较重；协同式 Saga 由事件驱动，耦合较低但全链路更难观察。选择取决于流程复杂度和团队维护能力。

### 幂等键

入口写接口要求客户端传唯一请求号：

```http
POST /orders
Idempotency-Key: 4c98a02d-...
```

服务端将“调用方 + 幂等键”建立唯一约束，重复请求返回首次结果。幂等记录与业务写入应在同一事务中完成。

## 可观测性

### 三类信号

| 信号 | 回答的问题 | 关键字段 |
| --- | --- | --- |
| 指标 | 系统整体是否异常 | QPS、错误率、P95/P99、饱和度 |
| 日志 | 某次失败发生了什么 | traceId、业务键、错误码、阶段 |
| 追踪 | 时间花在哪个服务 | span、父子关系、依赖与耗时 |

日志应结构化：

```json
{
  "level": "ERROR",
  "service": "order-service",
  "traceId": "4fd0...",
  "orderId": "ORDER-001",
  "errorCode": "INVENTORY_TIMEOUT",
  "durationMs": 352
}
```

不要把完整请求体统一打进日志，其中可能包含令牌、地址、手机号和支付信息。

### SLI 与告警

核心指标不仅看平均值：

- 可用率：成功请求数 / 有效请求数。
- 延迟：P50、P95、P99，按接口和下游拆分。
- 饱和度：线程池队列、连接池等待、CPU、内存和磁盘。
- 业务指标：下单成功率、支付完成率、消息积压。

告警应描述影响、范围、可能原因和操作手册链接，避免每次短抖动都通知全部人员。

## 发布与故障处理

### 灰度发布

1. 新旧版本契约和数据库结构向前兼容。
2. 先部署少量实例，观察错误率、延迟和业务指标。
3. 逐步扩大流量，异常时停止并回滚。
4. 所有消费者升级后再清理旧字段和兼容代码。

### 优雅停机

收到终止信号后：停止接收新流量，从注册中心摘除，等待在途请求和消息处理完成，提交进度，最后关闭连接池。直接杀进程会造成连接重置和重复消费。

### 故障排查顺序

1. 确认用户影响和开始时间。
2. 查看入口错误率、延迟和变更记录。
3. 沿 trace 找到最慢或失败的依赖。
4. 检查线程池、连接池、消息积压和数据库。
5. 优先止损：回滚、限流、熔断或关闭非核心功能。
6. 恢复后补齐时间线、根因、监控缺口和长期修复。

## 综合示例

### 综合示例：为远程调用设置明确边界

```yaml
dubbo:
  consumer:
    timeout: 1500
    retries: 0
    check: false
  registry:
    address: zookeeper://127.0.0.1:2181
```

示例要点：

- 写操作默认不要自动重试，除非接口具有幂等保证。
- 超时应根据下游耗时分布和上游总预算设置。
- 启动检查策略取决于服务是否允许降级运行。

## 常见误区

- 按数据库表而不是业务能力拆服务
- 没有超时和幂等设计就开启重试
- 将注册中心误认为业务数据存储
- 只看平均耗时，不观察 P95 / P99 和错误率

## 参考答案

### 1. 为创建订单接口设计幂等方案。

客户端携带唯一请求号；服务端使用唯一索引或原子存储记录处理结果；重复请求返回首次结果。

### 2. 为什么重试可能放大故障？

下游已经过载时，重试会增加请求量；多层重试还会呈乘法放大，应限制次数、退避并设总预算。

### 3. 服务拆分前至少要明确哪些边界？

业务职责、数据所有权、调用契约、失败处理、团队所有权和独立发布价值。

### 4. 如何从入口 SLA 反向设计下游超时？

先扣除入口本地处理、序列化和网络余量，再按关键路径给各下游分配预算；并行调用按最长分支计算，串行调用需要相加。任何下游超时都必须小于上游剩余预算。

### 5. Saga 补偿和数据库事务回滚有什么区别？

数据库回滚撤销同一事务内尚未提交的写入；Saga 补偿是在多个本地事务已经提交后执行新的业务动作，例如释放库存或返还优惠，可能失败，因此必须幂等、可重试和可人工介入。
