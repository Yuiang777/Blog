## 核心内容

### 消息模型补充

- **Topic**：一类消息的逻辑集合。
- **Partition**：并行与有序的基本单位；同一分区内有序。
- **Consumer Group**：组内消费者分担分区，组间独立消费。
- **Offset**：消费者在分区中的读取进度。
- **Replica**：分区副本用于容错，不等于额外的消费并行度。

生产设计默认假设消息可能重复。消费者应以业务唯一键建立幂等记录，在业务处理成功后再提交消费进度。失败消息必须有受控重试次数、退避和最终告警。

### Kafka 原始记录

#### Kafka

**kafka消息堆积了怎么办？**

- 首先通过kafka-consumer-group.sh看consumer group的lag指标是否堆积，再看是所有partition的堆积还是单个分布的堆积。
- 再通过监控系统或者JMX指标来查看看消费速率是生产的慢还是消费的慢，如果消费小于生产那么就会堆积。

解决：

- 如果是bug就处理bug，可以临时添加分区来处理线上问题。
- 增加消费者的线程数量
- 增加消费者实例：在分布式系统中可以水平扩展多个消费实例，来进行消费
- 优化消费者的逻辑：减少单个消息的处理时间，比如减少I/O操作、减少批处理操作，异步消费，批量消费。
- 要注意一个topic的分区/队列要大于消费实例，不然消费者就没有消息消费，因为一个分区只能被一个消费组的一个消费者消费
- 还可以进行限流或者降级操作，把没有的消息丢弃或者延迟处理


**一个分区只能被一个消费者组的一个消费者消费的原因**

因为kafka内部的partition分区在一个consumer group中只能有一个消费者消费，要保证信息消费的顺序性，同时避免多个消费者竞争offset导致重复消费或者数据不一致性，并简化了offset的管理。可以添加partition，消费者实例的数量以及在消费端添加多线程和批量处理来提升消费能力。

## 消息队列的角色与语义

### 为什么要引入消息队列

消息队列主要解决三类问题：

- **异步**：主流程完成后再处理通知、搜索索引、统计等非关键任务。
- **解耦**：生产者只发布业务事实，不直接依赖所有下游实现。
- **削峰**：用队列吸收短时流量，由消费者按可承受速度处理。

它也会引入新的复杂度：重复、延迟、乱序、积压、消息结构演进和跨服务一致性。若一次操作必须立即知道结果，且调用链短、失败语义明确，同步调用可能更合适。

### 事件、命令与通知

| 类型 | 示例 | 命名建议 | 特点 |
| --- | --- | --- | --- |
| 领域事件 | 订单已支付 | `OrderPaid` | 描述已经发生的事实，不要求唯一消费者 |
| 命令 | 为订单创建配送单 | `CreateDelivery` | 指定期望动作，通常由一个处理方负责 |
| 通知 | 发送支付成功短信 | `PaymentSmsRequested` | 偏技术任务，应允许失败和降级 |

事件名使用过去式，载荷包含事件 ID、业务主键、发生时间、schema 版本和必要快照。不要把数据库整行或超大对象直接发送出去。

```json
{
  "eventId": "01J5M9X7Y8Q2...",
  "eventType": "OrderPaid",
  "schemaVersion": 2,
  "occurredAt": "2026-08-19T08:30:00Z",
  "aggregateId": "ORDER-20260819-001",
  "data": {
    "userId": 1024,
    "amount": 3590,
    "currency": "CNY"
  }
}
```

## Kafka 核心机制

### Topic、Partition 与 Replica

- Topic 是消息的逻辑分类。
- Partition 是并行、顺序和存储的基本单位。
- 同一分区内消息按 offset 有序，不同分区之间没有全局顺序。
- Replica 提供副本容错；Leader 处理读写，Follower 同步数据。
- Consumer Group 内一个分区同一时刻只分配给一个消费者实例。

分区数决定消费组的最大有效并行度，但不是越多越好。分区过多会增加元数据、文件句柄、选主和重平衡开销。规划时考虑峰值吞吐、消费者处理速度、未来扩容和顺序要求。

### 分区键设计

需要保证同一订单事件有序时，以订单 ID 作为 key：

```text
partition = hash(orderId) % partitionCount
```

好 key 应满足：业务相关、分布相对均匀、长期稳定。使用固定常量会让所有流量进入一个分区；使用随机 key 会失去同一实体的顺序。

增加分区数后，`hash(key) % partitionCount` 的结果可能改变，所以跨扩容前后的全局实体顺序不能想当然。消费者仍应校验业务版本或状态。

### Offset 与消费进度

Offset 是消息在分区中的位置。消费者处理完成后提交 offset，表示该位置之前的消息已经处理。常见风险：

1. **先提交、后处理**：进程在处理中崩溃会丢业务处理。
2. **先处理、后提交**：提交前崩溃会重复处理。
3. **自动提交**：提交时机与真实业务完成时机可能不一致。

关键业务通常关闭自动提交，在业务成功后手动提交，并通过幂等处理承受重复投递。

## 可靠生产

### 生产者确认

Kafka 常见关键配置：

```properties
acks=all
enable.idempotence=true
retries=10
delivery.timeout.ms=120000
request.timeout.ms=30000
max.in.flight.requests.per.connection=5
```

`acks=all` 表示等待所有同步副本确认；幂等生产者减少重试导致的重复写入。它解决的是单个生产者会话内的 Kafka 写入重复，不等于业务端到端幂等。

发送必须处理异步回调，记录 topic、partition、offset、事件 ID 和失败原因。不能只调用 `send` 后立即认为消息已经可靠到达。

### 数据库与消息的一致性

直接执行“提交订单事务，然后发送消息”存在两个窗口：数据库成功但消息失败，或消息成功但数据库回滚。常用 Outbox 模式：

```sql
BEGIN;

UPDATE orders
SET status = 'PAID'
WHERE id = :order_id AND status = 'WAITING_PAYMENT';

INSERT INTO event_outbox(event_id, aggregate_id, event_type, payload, status)
VALUES (:event_id, :order_id, 'OrderPaid', :payload, 'NEW');

COMMIT;
```

后台发布器扫描 Outbox，将事件发送到 Kafka，成功后标记为已发布。扫描器必须支持并发抢占、失败重试和长期未发布告警。消费者仍需幂等，因为发布器可能在“发送成功但状态未更新”时重发。

## 可靠消费与幂等

### 幂等处理的几种方式

1. **事件表唯一约束**：以 `event_id` 建唯一索引，处理过则直接返回。
2. **业务条件更新**：只允许符合当前状态的变更，例如待支付到已支付。
3. **业务键唯一约束**：如同一订单只能创建一个配送单。
4. **幂等结果缓存**：适合短期防重，不能替代最终数据库约束。

```sql
BEGIN;

INSERT INTO consumed_event(consumer_name, event_id, consumed_at)
VALUES ('delivery-service', :event_id, NOW())
ON CONFLICT DO NOTHING;

-- 只有插入成功才继续执行业务写入
INSERT INTO delivery_order(order_id, status)
VALUES (:order_id, 'CREATED')
ON CONFLICT (order_id) DO NOTHING;

COMMIT;
```

去重记录与业务更新应在同一事务内，否则仍可能只完成其中一步。

### 重试与退避

错误先分类，再决定动作：

| 错误类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 瞬时错误 | 网络超时、依赖短暂不可用 | 有上限的指数退避重试 |
| 数据错误 | schema 不兼容、字段缺失 | 进入死信，等待修复 |
| 业务冲突 | 非法状态迁移、资源不存在 | 记录原因，按业务规则补偿 |
| 系统性故障 | 数据库整体不可用 | 暂停消费或触发熔断，避免重试风暴 |

重试 Topic 可以按延迟分层，例如 `order.retry.1m`、`order.retry.10m`。每次重试都要增加计数并保留首次失败时间，避免消息无限循环。

### 死信队列不是垃圾桶

死信消息至少保留：

- 原 topic、partition、offset 和 key。
- 原始 payload 与 schema 版本。
- 消费者名称、异常类型和错误摘要。
- 首次失败时间、最后失败时间和重试次数。
- trace ID 与业务主键。

必须提供查询、告警、修复和安全重放流程。重放前确认消费者已经修复且仍具备幂等性。

## 顺序、重平衡与积压

### 业务顺序不能只依赖 Kafka

即使同一 key 进入同一分区，重试 Topic、人工重放或上游迟到仍可能造成业务乱序。事件中可增加 `aggregateVersion`：

```text
OrderCreated(version=1)
OrderPaid(version=2)
OrderCancelled(version=3)
```

消费者维护已处理版本。收到旧版本时忽略，遇到跳号时延迟处理或查询权威数据源，不盲目覆盖新状态。

### Consumer Group 重平衡

消费者加入、退出、订阅变化或分区变化会触发重平衡。期间分区重新分配，处理暂停。降低影响的方法：

- 保持消息处理时间小于 `max.poll.interval.ms`。
- 长任务拆分或转交专门执行器，持续调用 poll。
- 使用合作式重平衡策略减少全部分区同时停顿。
- 优雅停机，停止拉取、等待在途任务、提交成功 offset 后退出。

### 积压处理

先比较生产速率和消费速率，再判断扩容是否有效。若单条处理依赖慢 SQL，单纯增加消费者会把压力转移到数据库。

积压排查顺序：

1. 哪些 topic 和 partition 出现 lag，是否数据倾斜。
2. 消费吞吐下降还是生产流量上升。
3. 消费耗时花在反序列化、业务计算还是外部依赖。
4. 是否发生频繁重平衡、异常重试或死锁。
5. 扩容、限流、暂停非关键生产或离线重放的风险。

## Schema 演进与可观测性

新增可选字段通常更容易向后兼容；删除、改名和改变字段语义风险较高。消费者应忽略未知字段，生产者在所有消费者升级前保留旧字段。重要事件可以使用 Schema Registry 统一校验兼容性。

生产环境至少监控：

- 生产成功率、发送延迟和重试次数。
- Consumer lag、消费速率和单条处理耗时。
- 重平衡次数、消费者实例数和分区分配。
- 重试 Topic 数量、死信数量和最老死信年龄。
- Broker 磁盘、ISR 缩减、请求延迟和网络吞吐。

告警要能关联事件 ID、业务主键和 trace ID，但日志中避免输出密码、令牌和完整个人信息。

## 综合示例

### 综合示例：幂等消费伪代码

```java
@Transactional
public void handle(OrderCreated event) {
    if (processedEventRepository.exists(event.eventId())) {
        return;
    }
    orderProjection.apply(event);
    processedEventRepository.save(event.eventId());
}
```

示例要点：

- 幂等记录与业务变更放在同一数据库事务中。
- 消息键可选择聚合根 ID，使同一业务对象进入同一分区以保持顺序。
- 不要无限重试不可恢复错误，应进入死信或人工处理流程。

## 常见误区

- 把消息队列当作同步 RPC 的透明替代
- 承诺全局顺序却配置多个分区
- 业务成功前提交 offset 导致消息丢失
- 没有 schema 版本和向后兼容策略

## 参考答案

### 1. 如何保证同一订单的事件有序？

用订单 ID 作为消息 key，使同一订单进入同一分区；消费者仍需校验事件版本，处理重放和迟到消息。

### 2. 为什么“至少一次”要求消费者幂等？

故障恢复、超时或提交 offset 失败都可能导致重复投递，相同事件不能重复产生业务副作用。

### 3. 什么消息适合进入死信队列？

多次重试仍失败、格式不可解析或违反业务约束的消息；死信必须保留原因、原消息、重试次数和可追踪标识。

### 4. Outbox 发布器在消息发送成功后、更新状态前崩溃会怎样处理？

恢复后发布器会再次发送同一事件，因此事件必须有稳定 `eventId`，生产与消费链路都要支持重复。消费者用事件唯一约束或业务条件更新保证幂等。

### 5. Consumer lag 快速增长时应该按什么顺序排查？

先确认具体 topic 和 partition 是否倾斜，再比较生产与消费速率，检查单条处理耗时、下游依赖、异常重试和重平衡。找到瓶颈后再决定优化、扩容、限流或暂停非关键生产。
